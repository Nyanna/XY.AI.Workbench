          }

              return Err(Error::NameConflicts(duplicates));

              project.objects.insert(located.object);
          }

                  project.objects.attach(&owner, &block.body, block.names);
              }
          }
          project.objects.resolve_dependencies();

1. `cargo` will ein Crate kompilieren und ruft normalerweise `rustc <argumente>` auf.
2. Wegen `RUSTC_WORKSPACE_WRAPPER` ruft es stattdessen `rustir-driver rustc <argumente>` auf. Das gilt für alle Crates deines Workspaces. Fremde Abhängigkeiten wie `serde` und `candle` gehen weiter direkt an `rustc`.

`rustir` liefert die Quelltexte (Bodies), der Treiber die exakten Abhängigkeiten, und `--edges` führt beide zusammen.

Genau das ist der Fall, der die Regel kompliziert macht. Ich trenne ihn in zwei Fälle.

**Fall 1: B steckt in A, und nur B nutzt P**
```
A (pub) ──► B (pub) ──► P (privat)
```
A erreicht P nur über B. P gehört allein B, weil nur B es direkt benutzt. Der Weg über B reicht A. Das ist die Kindliste, die du vorgeschlagen hast. Der Eigentümer ist also nicht jedes Objekt, das P irgendwie erreicht, sondern nur die Objekte, die es direkt benutzen. Eine direkte Nutzung durch ein anderes öffentliches Objekt gilt nicht als Weg.

**Fall 2: A und B nutzen P direkt**
```
A (pub) ──► P (privat) ◄── B (pub)      (A ──► B oder nicht)
```
Hier gibt es zwei direkte Nutzer. Das gilt auch, wenn A zusätzlich B benutzt. P kann dann nicht in der Kindliste von nur einem der beiden stehen.

Kopieren ist hier gefährlich: Eine Kopie von P in beide Eigentümer wären zwei verschiedene Typen. Ein `static`, ein `Mutex` oder ein Zähler hätte plötzlich zwei getrennte Zustände. Das ändert das Verhalten, obwohl der Code kompiliert. Ich würde deshalb nicht kopieren.
